# Shared Access Count Overflowed

Title: fixed
Family: runtime

## Explanation

A `WritableSharedReference<T>` counts its active readonly accesses. Each `acquireReadonlyAccess()` adds one until its access object is destroyed. This panic means the count was at its maximum and the program asked for another readonly access.

The maximum is larger than the number of access objects a program can keep in memory, so a program that ends its accesses does not reach it.

## Fix

Hold fewer readonly accesses to the value at one time. Look for a loop that calls `acquireReadonlyAccess()` and keeps every access object, and end each access when its work is done. A standalone block `{ ... }` ends an access at its closing brace.

## Example

No program raises this code on demand: the count holds more active accesses than a program can keep in memory, so the limit is out of practical reach. A program could meet it only by holding an extreme number of readonly accesses to one value at the same time.
